# DeepSeek 方案对照评审

日期：2026-10-17。结论：保留现有主架构，吸收发现流程、关系注册表和交付追踪方面的细化；调整少数开发依赖与验收条件，不整体替换规划。

本次核对了用户粘贴的 DeepSeek 摘要、现有四份设计文档及相关源码。摘要提到的 v0.2 全文、research 文件和测试原始记录未在本次检查的目录中取得。因此，对它们的内容和测试结果不作独立确认。本文是评审及修订建议，没有修改原 US、SDD、实施计划或运行代码。

## 1. 总体差异

两份方案在主架构上基本一致：新建轻量流程；数据库/Excel 与 Markdown 两通道；模型提出结构假设，程序验证并编译规则；DISTINCT 投影；共享实体与来源支持分离；按分区增量对账；不保存数据库返回数据。

DeepSeek 摘要的主要增量在工程分解：把发现 workflow 独立成文档，分为五类任务；显式提出关系注册表、规则回滚、交付批次和夹具台账。它给出的工时更保守。

我们的原计划已经写明 xiaomeng 没有数据库执行入口、两类文档需要新建、route2 不支持宽 L1…L5、语义列关系缺失，以及多处本地持久化必须改造。这些属于双方共识，不能计为新增需求或额外开发阶段。

## 3. 值得采纳的具体内容

### 3.1 单独定义发现任务契约

原 SDD 的 [发现流程](SDD.md:189) 已有框架，但任务输入输出尚未细到可以直接写接口。DeepSeek 提出的独立 `DISCOVERY_WORKFLOW.md` 有实际价值，建议下一次修订补充它。

五类任务可以作为调度器任务类型：列组发现、跨表关联、层级发现、文档解释、反例修订。层级可以从表内发现中单独调度，便于预算和验收。反例首先由确定性检查产生，只有需要重新解释含义时才调用模型，不要求每轮都调用五次模型。

每个任务至少明确：

- 输入：目标、授权对象 ID、列组 ID、相关文档版本、临时观察、当前假设及依赖。
- 输出：结构化假设、所需验证算子、备选解释、排除条件、未知项。
- 验证：哪些检查在样本上成立，哪些要查询完整目标范围，哪些属于业务语义证据。
- 状态：提议、探查中、待修订、已验证、预算不足、不支持、失效。
- 恢复：如何仅用已接受规则、状态和结果重新取数，不能持久化临时样本包。

模型只能引用已知对象 ID；程序拒绝虚构字段、任意 SQL 和执行代码。任务个数和类型可扩展，不因此扩大自主工具权限。

### 3.2 将关系注册表前移

原 SDD 已列关系类别，但缺少统一的逐关系契约。建议基础阶段先定义：

`relation_kind / source_kind / target_kind / direction / qualifiers / required_evidence / validation_policy / identity_effect / version`。

例如 `same_attribute_role` 允许列/属性角色对齐，不触发实体合并；`verified_reference` 必须有键、范围和引用验证；`same_entity` 需通过身份校验和冲突检查，不能因模型输出一条同义边就自动合并整组节点。

界面读这个注册表生成图例和详情。结构模型先定，界面随后，避免前端和发现器各自解释“关联”。

### 3.3 增加从需求到测试的追踪矩阵

每条 US 对应：规则/接口、测试夹具、真值文件、失败样例、执行记录、当前状态。未实现的夹具列 planned，不以文档列出了名字就算交付。

优先补三个明确验收点，而非为了凑 28 条重排全部编号：

1. 只有 `l2_code/l2_name` 一组列时，识别为实体列组，不凭 l2 生成父子关系。
2. 规则回退后，用当前数据重验；不能把旧图结果表示为当前源库事实。
3. 报错、取消、模型原文转发和重试路径不能保存样本；不能只检查成功路径没有文件。

### 3.4 明确规则回滚的两种含义

**规则回退：** 从 v3 切回 v2 的执行定义，检查其与当前 schema/文档是否兼容，再对当前来源重算受影响分区并发布。这不会恢复过去的源数据。

**历史结果查看：** 若保留了历史图谱结果，可以查看旧发布版本，但它带历史时间和来源状态，不能称为当前验证结果。

本项目不保存源行快照，不能承诺重演历史单元格。回滚还必须联动身份绑定、属性值、别名和关系支持；只换 RuleSpec 文件会留下旧语义结果。

## 4. 需要修改或限定的说法

### 4.1 “SQL AST、事件与脱敏可以直接带走”过于宽泛

[xiaomeng/sql_ast.py:47](/Users/sanjiuganmaoling/Desktop/code/xiaomeng/src/xiaomeng/sql_ast.py:47) 存在容错解析和截断尾部恢复，只适合历史 SQL 证据理解。安全执行需要严格解析完整语句，不能把这个类直接放进只读网关。

[xiaomeng/pipeline.py:79](/Users/sanjiuganmaoling/Desktop/code/xiaomeng/src/xiaomeng/pipeline.py:79) 的 `_redacted_error` 仅替换 API key；同文件 111–114 行会转发模型 `content_delta`，[usage_log.py:33](/Users/sanjiuganmaoling/Desktop/code/xiaomeng/src/xiaomeng/usage_log.py:33) 还会保存传入事件。这不满足“不保存数据库返回数据”的要求。可复用事件结构，但数据内容必须重新定义白名单，追踪/持久化接收端也要受约束。

七个导出模型在 [schemas.py:18](/Users/sanjiuganmaoling/Desktop/code/xiaomeng/src/xiaomeng/schemas.py:18) 中可以确认。但 [models.py:235](/Users/sanjiuganmaoling/Desktop/code/xiaomeng/src/xiaomeng/models.py:235) 等契约含 `matched_values/payload`，其来源指针、身份范围、属性支持和状态不自动满足新契约；迁移前逐项适配。尤其不能丢掉现有 SDD 的属性级来源支持和分析主张的模态。

### 4.2 不应按 `results.sqlite` 这个文件名决定禁止结果存储

[storage.py:279](../../code/ontology_r2/storage.py:279) 的 Sink 同时承担结果存储；[pipeline.py:1049](../../code/ontology_r2/pipeline.py:1049) 又把对象、断言和 evidence 放进它。因此**原 Sink 不可原样复用**，因为允许原始证据混入。

还有一个具体风险：[relations.py:62](../../code/ontology_r2/relations.py:62) 在同一数据库建立搜索索引，[relations.py:117](../../code/ontology_r2/relations.py:117) 将完整 target 行序列化写入。因此，DeepSeek 点名旧 `results.sqlite` 有依据，迁移台账应覆盖它的搜索表和原始证据，而不只检查 items 中的图对象。

但用户允许保存抽取结果。正确规则是：源结果、样本、原始证据禁止；合格图事实和维护状态允许进入客户指定存储。是否使用 SQLite、关系库或图数据库是另一项选择。不能把“禁止原始返回数据”扩大成“禁止任何结果数据库”。

同样，缓存的对象必须区分：禁止样本和源投影缓存；已验证规则、非值化任务状态、已发布图结果可以持久化。旧离线项目保留原模式，新模式隔离旧持久化路径，不执行全仓删除。

### 4.3 “相邻非空层连接”需要条件

`A → NULL → C` 可能是中间层缺失，也可能是合法跳级。自动连接 A→C 会制造未经证实的直接父子关系。

保留 [原 SDD 的规则](SDD.md:312)：默认缺层待决；只有数据说明与验证支持最近非空祖先语义，才使用该模式。连续重复同身份压缩与跳过未知空层不是同一操作。

### 4.4 “预算小，所以不能发现”只解释了一部分

[association_rules.py:51](../../code/ontology_r2/association_rules.py:51) 确实默认 3 次模型调用、8 次工具调用、3 次全扫描。但 [同文件 25–46 行](../../code/ontology_r2/association_rules.py:25) 更关键：提案只能引用已有候选字段对、selector、scope_bindings 和少数变换，根本不能表达实体列组或宽层级规则。

即使增加预算，这个 DSL 也不会自动具备新能力。应先扩展任务和算子表达力，再测量预算；单次实验里的候选核验比例不能证明模型能力不足，更不能证明五类任务一定有效。若该实验关闭了 Agent，更不能以其结果评价 Agent 探索能力。

默认值也不等于所有运行的实际值：配置可以覆盖；当前 [runtime.fruit-probe.yaml:37](../../config/runtime.fruit-probe.yaml:37) 就关闭了 Agent，并设置小实验的核验上限。应按配置和代码能力分别评估。

### 4.5 不固定承诺“核验保底 40%”

预留核验资源是正确的；40% 没有在本次材料中给出标定依据。DB 查询、模型 token 和内存不能混成一个百分比预算。

建议每次接纳新假设前估算最低验证成本，只有剩余预算覆盖时才启动；估计偏差或执行超时仍返回 partial。分别保留 DB、LLM、返回字节/内存的硬限制，任务数和修订轮数作为调度配额。40% 可作为某一池的实验初值，不作为准确率或完成率保证。

### 4.6 不应把技术边的 unresolved 直接改为业务“已确认”

[association_rules.py:148](../../code/ontology_r2/association_rules.py:148) 明确让技术关联的 `semantic_relation` 保持 unresolved；[metadata_graph.py:137](../../code/ontology_r2/metadata_graph.py:137) 按技术关联展示。这是在避免“值相等等于业务关系”的错误。

应保留技术证据层，另外产生有独立依据的语义角色边、概念映射或业务边。问题在于缺少后一层，不能通过更改 technical_link 的状态来补。

“列关系看不清”也包含两个不同问题：已有技术列边在默认折叠视图下不直观；所需的语义角色边尚未进入统一模型。新模型与交互都要改，不必争一个统一主因。

### 4.7 “规则/结构/文档不变，模型调用为 0”需加前提

原样重跑、重复事实或符合已确认模式的新成员，确实无需逐行调用模型。但字段结构不变时也可能出现未知判别值、同码异义或新口径；此时需要定向复核。

验收应写成：**规则及依赖不变，且新增数据满足已确认模式时，确定性执行不调用 LLM；出现语义例外时，只复核受影响模式。** 数据内容违反规则不能因 schema 没变而被忽略。

## 6. 建议修改的开发顺序

| 阶段 | 保留 | 调整建议 |
| --- | --- | --- |
| P0 契约与真值 | 两条输入、目标、固定样例 | 加关系注册表；冻结节点/属性/边/主张支持契约；建立 US→夹具→真值→结果台账 |
| P1 连接与安全 | Gauss/Excel/Markdown、只读网关、不落盘 | 增加存储可达路径审计；先交付无模型的最小完整流程；不要只实现基础设施 |

| P3 层级与发布 | 宽层级、共享实体、首次发布 | 同期验证最小撤回：A/B 共享，撤回 A 的独有别名，B 保留；禁止只做 union/upsert |

首个可运行里程碑：小规模 Gauss/Excel + 一份说明 Markdown，已确认 RuleSpec 执行列组和宽层级，生成合格图结果，重复运行幂等，成功/失败均无原始数据落盘。随后接入自动规则发现，对照人工真值规则。分析文档通道仍在完整首版范围内，不因最小里程碑暂缓而删除。

## 7. 工期和测试证据

原估计为 35–49 人日；DeepSeek 为 46–59 人日。后者对 Gauss 适配、保留策略验证、规则执行和试点的预留更保守，适合作风险讨论的参考，但两者都是估计，不能从摘要中确认真实开发效率。

不建议把七个阶段的规划直接转成承诺日期。先完成接入、安全与一条完整的小实验，再按新增模块量、实际 Gauss 兼容问题和反例修复时间更新估计。首两周可以作为检查点，不保证届时已具备所有阶段能力。

摘要中的“4 个文件、21 个用例通过”和“2,946 候选、600 核验、923 模式仅查 24”等记录，本次没有取得对应命令、版本和运行产物，未作为独立确认事实。即使全部属实，也只能说明相关旧代码和那次实验，不能证明新 workflow、安全执行或 Gauss 能力已验收。

## 8. 本次建议的最终取舍

- **保留：** 两条输入、SQL 下推、规则执行、共享身份、属性级支持、不完整读取不撤回、两类文档和源数据禁存边界。
- **采纳：** 独立 workflow 规格、五类任务、关系注册表、规则生命周期、交付追踪矩阵、更加保守的实施预留。
- **修正后采纳：** 代码复用范围、写盘清理、核验预算比例、缺层连接和零模型调用条件。
- **后置：** 千万行演练、多产品适配和非必要基础设施。

因此需要的是有针对性的规划修订，主架构与客户范围保持不变。没有必要把旧文档整体换成摘要里的新版本，也不应在尚未取得完整 v0.2 文档时声称已经完成全文合并。

# 轻量知识图谱改造：结论与代码核查

状态：设计建议，尚未实现。核查日期：2026-10-17。本次不修改两套项目的运行代码，不连接客户数据库，不调用抽取模型。

阅读顺序：[结论与代码核查](README.md) → [用户故事 US](US.md) → [系统设计 SDD](SDD.md) → [实施与验收计划](IMPLEMENTATION_PLAN.md)。US 表示用户故事，SDD 表示软件设计说明。

## 1. 结论

两个项目可以共同支撑新需求，但需要新增一条以“结构发现 → 规则验证 → SQL 投影 → 图谱发布”为主的流程。直接拼接两套现有 pipeline，会保留全量本地导入、按证据包抽取和本体类型推导等与新需求不匹配的行为。

建议新建独立的 `lightgraph` 包，复用经过适配的模块和测试。旧 `route2` 与 `xiaomeng` 保留原入口，作为迁移对照。新项目的两个输入通道是：

- **结构化数据通道：** Gauss 数据库的完整授权元数据及按需查询的实例数据；或用户上传的 Excel。二者进入同一套结构发现和规则执行流程。
- **知识文档通道：** Markdown 等知识文档。数据说明文档在发现规则时参与解释；分析知识文档抽取独立的分析概念、方法和适用条件，并连接到已有图谱。

BI 组件、历史 SQL、血缘是可选的补充来源。没有这些资料时，系统也必须能工作，不能继续要求 xiaomeng 的六类报表 JSON 全部齐备。

用户已明确：数据库是 Gauss 系列；**抽取结果允许保存，数据库检索返回的数据不允许保存。** 因此，禁止保存结果集、样本、原始投影表、含样本的模型输入、完整响应轨迹及来源数据库副本。不能把这些东西改名成“证据”或“缓存”后继续保存。图谱里的业务名称等是经抽取规则选中的结果属性，必须与无选择的查询结果复制分开。

## 3. 对需求逐项判断

| 需求 | 是否可行 | 关键条件与边界 |
| --- | --- | --- |
| 只读 SQL、按需取数、不保存返回数据 | 可行 | 安全算子生成 SQL、AST 校验、数据库最小权限、只读事务共同约束；禁用原始数据日志及持久化 |
| code/cn_name/en_name 合为实体，sort 排除 | 可行 | 发现列组并检验“作用域+编码→属性”的依赖；名称相同不能代替身份判断 |
| 宽层级数据构建树 | 可行 | 宽转长、压缩连续重复身份、父子投影、环与多父检查；样例中不一致的编码不能擅自纠正 |
| 表列元数据图与跨表语义对齐 | 可行 | 物理关联、属性角色相同、实体等价分别表示，不共用一个“关联”标签 |
| 有探索能力的智能体 | 可行且有必要 | 在受控 workflow 中选择探查问题和算子；模型不直接执行任意 SQL，也不逐行抽取规则可表达的数据 |
| 千万事实压缩为少量知识 | 条件成立时可行 | 先确定所需知识的粒度，再对正确列组 DISTINCT；结果少不意味着数据库完全不用扫描 |
| 关键列不变时不再调模型 | 可行 | 按 schema/规则/文档契约复用规则；变化的实体取值通过规则批量处理 |
| 不扫描源表也精确发现全部更新删除 | 有条件 | 需要可靠变更源或完备版本机制；只有 SELECT 且没有变更记录时，必须允许源端投影重扫 |
| 说明文档与分析文档分别接入 | 可行 | 数据说明帮助解释，分析文档产生有出处的主张；两者都不能直接覆盖结构事实 |
| 字段名与值不一致的处理 | 部分自动可行 | 观察类型/分布/依赖冲突可以自动发现；完全缺乏语义证据时应保留未知，不能保证自动还原业务含义 |

## 4. 用“销售费用”说明新流程

输入列组：`report_item_l2_code`、`report_item_l2_cn_name`、`report_item_l2_en_name`、`report_item_l2_sort_column`。

1. 读取授权元数据和少量分层样本；读取适用的数据说明文档。字段名提供候选，不直接决定含义。
2. 模型提出列组：编码、中文标签、英文别名、展示排序。类型暂记 `ReportItem`，只有业务说明支持时再标为指标或财务科目。
3. 程序验证同一命名空间下编码是否稳定对应名称；多语言名称可以为空或有多个别名，不要求中英文互相唯一。
4. 在数据库执行针对这一列组的 DISTINCT，排除排序、事实金额、日期等与该实体身份无关的列。租户等上下文另形成引用结果。
5. 对 `(2150, 销售费用, Selling expense)` 生成一个语义实体，并建立它在来源列组、业务范围中的引用。排序值 112 不生成语义节点。
6. 再出现一万行相同实体，运行同一条规则即可；既不新增一万个节点，也不调用一万次模型。

但不能把所有表都做一次“删掉数值后 DISTINCT”。例如定义本身含单位、计算公式或统计口径，这些字段决定是否同一指标，必须进入身份规则。事实发生的日期通常不参与指标身份；定义生效日期则可能需要保留。列的作用取决于抽取目标和关系粒度。

## 5. 树样例需要先处理的数据矛盾

按用户提供的原始片段，`3 → 2 → 27 → 271 → 2711` 与 `3 → 2 → 27 → 271 → 2713` 是两条路径。若表头确认为 L1…L5，2711 与 2713 是同父的 L5 节点，不能凭编码前缀或缩进生成 `2711 → 2713`。

原始片段里的 `2/24/26/261/262/263/271/272`，与目标树中的 `28/2408/2608/2610/2620/2630/2710/2720` 不同。需要另有编码映射、数据说明或修订后的输入才能对应；自动发现程序应报告这些冲突。

`贡献利润(1)` 连续出现在多个层级，应合为一个实体，保留“在这些来源层级出现”的记录，不生成自环。L3/L4/L5 的重复有时是宽表补齐方式，但只有验证规则后才可压缩；跨层同码也可能存在局部编号碰撞。

## 6. 智能体究竟做什么

它的任务是提出、区分和检验规则假设。例如：

> “这四列可能是一组指标属性；在租户内，编码应决定中英文名称。先检查冲突编码，再检查不同层级的重复是否只是末级填充。”

程序执行针对这个假设的统计和反例查询。若有反例，模型调整规则：补充命名空间、拆分版本或保留待决。规则验证后冻结，后续取值只经过规则执行器。必要时新增一个发现任务，不能把全部行重新送回模型。

因此需要一个有状态的发现 workflow，但不需要让一群 Agent 无限制聊天。首期采用一个调度器、表内发现与跨表发现两类模型任务、一个独立确定性验证器即可。文档分析使用同一调度框架下的独立任务。具体状态、预算和算子见 SDD。

## 7. 首个可验收实验

用人工可核对的少量表和 Markdown 文档完成一条完整路径：

`Gauss/Excel + Markdown → 列组与层级发现 → 安全 SQL 核验 → DISTINCT 投影 → 唯一实体与父子边 → 文档知识关联 → 增量更新 → 表列对照展示`。

必须同时加入反例：重复行、跨租户相同定义、同名不同公式、同码不同命名空间、注释与值冲突、层级填充、缺层、多父、文档版本冲突。先做到规则正确、来源不落盘、重复运行幂等，再扩大表数。不能把“图变小”当作正确性验收。

## 8. 尚需在实施预检确认的环境信息

- “Gauss”具体是 GaussDB 的集中式/分布式、openGauss，还是其他产品；版本、兼容模式、部署系统和驱动包。当前不假定与 PostgreSQL 完全兼容。
- 是否提供现成的变更视图、更新时间、软删除标记或 CDC 消费接口。系统不自行给源库创建触发器、日志表或复制槽。
- 模型运行位置和请求保留策略。禁止源数据落盘必须覆盖模型网关、代理、追踪服务及崩溃转储。
- 图谱与规则结果的客户侧存储位置、访问范围。源库查询账户和结果存储账户分开。

这些是实施时的能力检查项，不影响先确定架构和开发顺序。
